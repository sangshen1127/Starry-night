## 0. 完成标准

这一阶段做完，必须同时满足：

- [ ] 数据库里有一个管理员账号，密码是 BCrypt 哈希（`$2a$` 开头）
- [ ] `POST /api/auth/login` 用 JSON 登录，成功后返回用户信息 + `Set-Cookie`
- [ ] 登录后调 `/api/auth/me` 能拿到当前用户
- [ ] 未登录访问 `/api/admin/**` 返回 **401 JSON**（不是登录页，不是 302）
- [ ] 已登录但权限不足返回 **403 JSON**
- [ ] `POST /api/auth/logout` 之后，`/api/auth/me` 又变回 401
- [ ] 任何接口的响应里都**不出现** `password` / `passwordHash`
- [ ] 前台接口（文章列表、详情、评论）依然匿名可访问

**注意**：M2 不追求"多角色权限"。单人博客只有一个管理员，别给自己加戏。

## 1. 先修一个已经开始写错的东西

你新建的 `entity/User.java` 里，有三个字段和表结构对不上：

| 你写的 | 表里的列 | 驼峰会映射成 | 结果 |
|---|---|---|---|
| `String name` | `username` | `name` | ❌ 列不存在 |
| `String password` | `password_hash` | `password` | ❌ 列不存在 |
| `String nickName` | `nickname` | `nick_name` | ❌ 列不存在 |

应该改成：

```java
@TableId(type = IdType.AUTO)
private Long id;
private String username;
private String passwordHash;
private String nickname;
private LocalDateTime createdAt;
private LocalDateTime updatedAt;
```

**三个都必须在写 Mapper 之前改完**，否则第一次查询就是 `Unknown column 'name'`。

另外，`passwordHash` 这个命名是刻意的：让人一眼看出"这是哈希，不是密码"，减少以后误用的可能。

## 2. 先看懂这张图，再动手

登录不是"查一下密码对不对"，它经过一条链：

```
浏览器 POST /api/auth/login {username, password}
        │
        ▼
SecurityFilterChain（这条路径 permitAll，放行）
        │
        ▼
AuthController.logIn()
        │  1. new UsernamePasswordAuthenticationToken(username, password)
        │  2. authenticationManager.authenticate(token)
        ▼
DaoAuthenticationProvider
        │  3. userDetailsService.loadUserByUsername(username)
        ▼
UserDetailsServiceImpl  →  UserMapper  →  SELECT * FROM users WHERE username = ?
        │  4. 拿到 passwordHash
        ▼
PasswordEncoder.matches(明文, 哈希)   ← BCrypt 内部做比对，不是字符串相等
        │
        ├─ 失败 → 抛 BadCredentialsException → Controller 捕获 → 401 JSON
        │
        └─ 成功 → 返回 Authentication
                    │
                    ▼
        5. 把 Authentication 存进 SecurityContext
        6. 把 SecurityContext 存进 Session（★ 最容易漏的一步）
                    │
                    ▼
        返回 JSON + Set-Cookie: JSESSIONID=...
```

**六个角色，各管一件事：**

| 角色 | 职责 | 你项目里对应 |
|---|---|---|
| `SecurityFilterChain` | 决定哪些路径要登录 | `SecurityConfig` |
| `AuthenticationManager` | 认证的总入口 | Spring 提供的 Bean，你注入 |
| `DaoAuthenticationProvider` | 真正执行"查人 + 比密码" | Spring 内置，不用写 |
| `UserDetailsService` | 按用户名查人 | 你自己实现 |
| `PasswordEncoder` | 哈希与比对 | `BCryptPasswordEncoder` |
| `SecurityContextRepository` | 把登录态存进 Session | `HttpSessionSecurityContextRepository` |

**你只需要写第 3、5 个**，其余都是配置。

## 4. 任务分解

### T2.1 修正 User，写 UserMapper

**做什么**

- 按第 1 节改字段
- `UserMapper extends BaseMapper<User>`，加一个按用户名查的方法（可以用 `selectOne` + `LambdaQueryWrapper`，也可以手写 SQL）
- 确认 `@MapperScan` 已经覆盖 `com.sangshen.mapper`

**验收**

- 启动无报错
- 在临时接口里 `selectList(null)` 能查出空列表（表里还没人）

**坑**：实体字段少一个 `ed`、`case` 写错，都会在第一次查询时报 `Unknown column`。看到这个错，先对着表结构逐列核。

---

### T2.2 实现 UserDetailsService + PasswordEncoder

**做什么**

1. 新建 `com.sangshen.security.UserDetailsServiceImpl`，实现 `UserDetailsService`
2. `loadUserByUsername` 里：
   - 调 `userMapper` 按用户名查
   - 查不到 → 抛 `UsernameNotFoundException`
   - 查到 → 返回 Spring 自带的 `User`（用 `User.withUsername(...).password(passwordHash).authorities("ROLE_ADMIN").build()`）
3. 单独建 `PasswordEncoderConfig`，注册 `BCryptPasswordEncoder` Bean

**为什么用 Spring 的 `User` 而不是让实体实现 `UserDetails`**

VBlog 那种"实体直接实现 UserDetails"的写法，会把数据库模型和框架模型绑死。用 `User.withUsername(...)` 更干净，实体只负责映射表。

**验收**

- 启动无报错
- 控制台不再打印 `Using generated security password`

**四个高频坑**

| 现象 | 原因 |
|---|---|
| 启动报 `NoSuchBeanDefinition: PasswordEncoder` | 定义了 UserDetailsService 但没提供 Encoder，两者必须成对 |
| 启动报 Bean 循环依赖 | Encoder 定义在 `SecurityConfig` 里，而 `SecurityConfig` 又依赖 UserDetailsService → 拆到独立配置类 |
| 登录永远失败，日志 `Encoded password does not look like BCrypt` | 数据库里存的是明文或者 MD5 |
| `UsernameNotFoundException` 被吞掉，返回 500 | 应该在 Controller 里捕获 `AuthenticationException` 转 401 |

---

### T2.3 初始化管理员账号（一次性）

**做什么**

- 新建 `config/AdminInitializer`，实现 `CommandLineRunner`
- 启动时判断 `users` 表是否为空；为空则插入一个管理员
- 用户名、密码从 `application.yml` 读（新增 `blog.admin.username` / `blog.admin.password`）
- 插入前用 `passwordEncoder.encode(...)` 加密

**为什么用代码而不是直接 SQL 插**

因为你需要 BCrypt 哈希。手写 SQL 只能插明文，或者去网上找在线生成器（不可信）。让程序自己加密最稳。

**验收**

- 启动后 Navicat 里看到一行，`password_hash` 形如 `$2a$10$...`
- 再次启动不会重复插入

**坑**：`CommandLineRunner` 每次启动都跑，必须判空；否则重启就多一个账号。

---

### T2.4 登录接口（本阶段最难）

**做什么**

1. `dto/LoginRequest`：`username`、`password`，加 `@NotBlank`
2. `AuthController` 注入 `AuthenticationManager`、`SecurityContextRepository`
3. 方法体顺序：
   - 构造 `UsernamePasswordAuthenticationToken(username, password)`
   - `authenticationManager.authenticate(token)` → 抛异常就是失败
   - 成功：`SecurityContextHolder.getContext().setAuthentication(auth)`
   - **把 context 存进 repository**（`repository.saveContext(context, request, response)`）
   - 返回 `Result.success(userInfo)`
4. 捕获 `AuthenticationException` → 401 `Result.error("用户名或密码错误")`

**`AuthenticationManager` 从哪来**

在你的配置类里加一个 Bean，参数是 `AuthenticationConfiguration`，方法体 `return config.getAuthenticationManager();`。

**为什么要 `SecurityContextRepository`**

因为 `SecurityContextHolder` 只在**当前请求**有效。请求结束，线程复用，里面的东西就没了。下一个请求要能认出你，必须把 context 写进 Session。**这一步是所有"登录成功但下一个接口还是 401"的根源。**

**验收**

用 IDEA 的 `.http`：

```
POST http://localhost:8080/api/auth/login
Content-Type: application/json

{"username":"admin","password":"你的密码"}
```

预期：

- 响应 `code: 1`，`data` 里有 `username`、`nickname`
- 响应头有 `Set-Cookie: JSESSIONID=...`
- **紧接着**发 `GET /api/auth/me`，返回同一个用户（说明 Session 生效）

---

### T2.5 me / logout

**做什么**

- `GET /api/auth/me`：从 `SecurityContextHolder` 取 `Authentication`，拿 username，再查库补 `nickname`，返回 `UserInfo`
- `POST /api/auth/logout`：`SecurityContextHolder.clearContext()` + `request.getSession(false).invalidate()`，返回成功

**验收**

- 登录后 `/me` 返回 200
- 登出后 `/me` 返回 401
- 登出后原来的 Cookie 再用也无效

**坑**：`getSession(false)` 可能返回 null（本来就没 Session），要判空，否则 NPE。

---

### T2.6 收窄权限规则

把 `SecurityConfig` 里的路径规则改成：

| 路径 | 规则 |
|---|---|
| `/api/auth/login` | `permitAll` |
| `/api/auth/me`、`/api/auth/logout` | `authenticated` |
| `/api/admin/**` | `authenticated` |
| `/api/**`（其余） | `permitAll` |
| `/error` | `permitAll` |
| `/uploads/**` | `permitAll` |

**顺序仍然重要**：具体的写在前面，`anyRequest()` 放最后。

**验收**

- 无痕窗口：`/api/admin/posts` → 401
- 登录后：同一地址 → 200（现在还没这个接口，可以先拿一个临时的 `/api/admin/ping` 验证）

---

### T2.7 401 / 403 返回统一 JSON

**做什么**

1. 实现 `AuthenticationEntryPoint`：往 response 写 `{"code":0,"message":"未登录或登录已过期","data":null}`，状态 401，`Content-Type: application/json;charset=UTF-8`
2. 实现 `AccessDeniedHandler`：同样格式，状态 403
3. 在 `SecurityConfig` 里注册 `exceptionHandling(...)`

**为什么必须做**

Spring Security 默认的 401 是空的，或者是一个 HTML 登录页。前端拦截器读 `response.data.message` 会拿到 `undefined`，弹窗一片空白。

**验收**

- 无痕窗口访问 `/api/admin/xxx`，响应体是 JSON，不是 HTML，也不是空
- `Content-Type` 是 `application/json`

## 5. 最容易卡住的地方：登录成功，下一个请求还是 401

这是 M2 的"分水岭"，90% 的人在这里卡过。

**原因**：`SecurityContextHolder` 是 ThreadLocal，请求结束就清空。你没把 context 写进 Session，下一个请求自然不认识你。

**排查顺序：**

1. 登录响应头有没有 `Set-Cookie: JSESSIONID=...`？没有 → 说明 Session 没创建
2. 下一个请求有没有带上这个 Cookie？没带 → 前端问题（`withCredentials` / 同域）
3. 带了 Cookie 还是 401 → context 没存进 Session

**三个解法，任选一个：**

| 做法 | 说明 | 推荐度 |
|---|---|---|
| 注入 `SecurityContextRepository`，显式 `saveContext` | 最清晰，能写出"为什么" | ★★★ |
| 手动 `session.setAttribute(SPRING_SECURITY_CONTEXT_KEY, context)` | 能跑，但用了内部常量名 | ★★ |
| 让 Security 的 `formLogin` 帮你处理 | 但你就得改成表单格式，和 JSON 契约冲突 | ★ |

选第一种，然后在代码里写一行注释说明"为什么必须存 Session"，以后你不会忘。

## 6. 测试用例

存成一个 `auth.http`，按顺序执行：

```
### 1. 未登录访问后台
GET http://localhost:8080/api/admin/ping
# 预期 401 + JSON

### 2. 错误密码
POST http://localhost:8080/api/auth/login
Content-Type: application/json

{"username":"admin","password":"wrong"}
# 预期 401，message 是"用户名或密码错误"

### 3. 正确登录
POST http://localhost:8080/api/auth/login
Content-Type: application/json

{"username":"admin","password":"你的密码"}
# 预期 200，Set-Cookie

### 4. 当前用户
GET http://localhost:8080/api/auth/me
# 预期 200 + username

### 5. 访问后台
GET http://localhost:8080/api/admin/ping
# 预期 200

### 6. 登出
POST http://localhost:8080/api/auth/logout
# 预期 200

### 7. 登出后再看
GET http://localhost:8080/api/auth/me
# 预期 401
```

IDEA 的 HTTP Client 会自动保持同一文件内的 Cookie，所以 3→4 能串起来。**如果你看到 4 返回 401，先确认 3 的响应头里有没有 `Set-Cookie`。**

## 7. 错误对照表

| 现象 | 最可能的原因 |
|---|---|
| `POST /api/auth/login` 返回 403 | CSRF 没关（你已经关了，确认 `csrf(...)` 那行还在） |
| 登录返回 302 跳转 | 请求被 Security 的默认表单登录截走了，检查路径是否和 `loginProcessingUrl` 冲突 |
| `NoSuchBeanDefinition: AuthenticationManager` | 没加 `AuthenticationConfiguration` 那个 Bean |
| 登录成功但 `/me` 401 | context 没存进 Session（第 5 节） |
| `Encoded password does not look like BCrypt` | 库里存的不是 BCrypt 哈希 |
| 启动报循环依赖 | Encoder 和 UserDetailsService 放在同一个配置类里 |
| 401 响应体是空的 | 没配 `AuthenticationEntryPoint` |
| 401 响应是 HTML | 同上，落到了默认登录页 |
| 重启后管理员账号重复 | 初始化没判空 |

## 8. 安全清单（做完逐条核对）

- [ ] 数据库里没有任何明文密码
- [ ] 接口返回里没有 `password` / `passwordHash` 字段
- [ ] 登录失败的消息统一为"用户名或密码错误"（不要区分"用户不存在"和"密码错误"，那会帮攻击者枚举账号）
- [ ] BCrypt 强度用默认 10，别调低
- [ ] Session Cookie 是 `HttpOnly` + `SameSite=Lax`（`application.yml` 已配）
- [ ] 生产环境 `secure: true` + HTTPS
- [ ] 初始化管理员的默认密码，上线前必须改掉

**可以后面再做的**（别现在做）：登录失败限流、记住我、多角色、OAuth 登录。

## 11. 不要做的事

| 不要 | 原因 |
|---|---|
| 上 JWT | 你选的是 Session，两套机制会打架 |
| 加 `@EnableMethodSecurity` | 单角色用不上，增加理解成本 |
| 自己写 Filter 替代 Security | 你还没到需要它的阶段 |
| 做注册功能 | 个人博客不开放注册，管理员由初始化脚本创建 |
| 做"记住我" | 多一套 token 机制，等有真实需求再说 |
